# Agenda 2.0 — Etapa D — materialização IANA (design)

> Data: 2026-07-18 · Status: **aprovado para virar plano de implementação**
> Origem: continuação do design mestre
> `2026-07-16-agenda-2.0-disciplina-aware-design.md` (§4 invariantes 1–4, §7
> Etapa D). Etapas A–C entregues; esta etapa gera as ocorrências `session` a
> partir das regras `agendamento_recorrente`.

## 1. Objetivo e recorte

A Etapa C cria regras recorrentes (`agendamento_recorrente`) mas grava **0
linhas `session`** (regra C1). A regra é só a intenção standing; o calendário
concreto ainda não existe. A Etapa D fecha isso: **materializa** as ocorrências
de cada regra em linhas `session` reais, de forma **idempotente**, **IANA-correta**
(sem offset fixo congelado) e **respeitando bloqueios**, mais o ciclo de vida da
regra ("esta e futuras" / "estender").

Escopo (design mestre §7):

- **Materialização IANA:** naive (`diaSemana` + `horaInicio` em `time`) →
  `timestamptz` resolvido na zona `clinic.timezone` **no momento da geração**.
- **Idempotência:** rodar a materialização N vezes não duplica ocorrência.
- **Rolling on-demand + "estender":** gera até um horizonte (default 12 semanas);
  botão estende o horizonte adiante. **Sem cron** na v1 (dívida mantida).
- **"Esta e futuras":** encerrar/editar regra fecha `vigenciaFim` e remove só as
  ocorrências **futuras `agendada`**; passado (`realizada`/`falta`) preservado.

Fora de escopo (dívida consciente, mantém spec mestre §2): cron automático,
grupo/co-terapia (v1 é 1:1:1), regras de faturamento/glosa.

## 2. Fatos do código já existentes (não reescrever)

Confirmados nesta sessão lendo `src/db/schema.ts` e `db/migrations/`:

- **Idempotência já garantida no banco:** índice único parcial
  `uq_session_recorrente_agendada (recorrente_id, agendada_para) WHERE recorrente_id IS NOT NULL`
  (`schema.ts`). Materialização usa `ON CONFLICT DO NOTHING` sobre ele.
- **Anti duplo-book já garantido no banco:** `session_no_overbook_terapeuta` e
  `session_no_overbook_paciente` — `EXCLUDE USING gist` sobre
  `tstzrange(agendada_para, session_fim(agendada_para, duracao_min))`, ambos
  `WHERE (estado = 'agendada')` (migration `0035`). As ocorrências
  materializadas nascem `estado='agendada'` → **estão sujeitas a estas
  constraints** (SQLSTATE `23P01` em colisão).
- **Fuso:** `FUSO_CLINICA = "America/Sao_Paulo"`, `FUSO_CLINICA_OFFSET = "-03:00"`
  (`agenda/fuso.ts`). SP não tem horário de verão desde 2019 (offset estável),
  **mas** o design mestre (inv1) exige resolução IANA para portabilidade e caso
  o DST volte — por isso o núcleo não usa o offset fixo.
- **Conversão instante→local já existe:** `paraMinutosLocais(instante, fuso)`
  (`lib/agenda/fuso-min.ts`), usada na leitura. A Etapa D adiciona o **inverso**
  (local→instante).
- **`carregarSemana`** hoje só lê avulsas (`isNull(recorrenteId)`); a Etapa D
  adiciona a leitura das materializadas (`recorrenteId IS NOT NULL`) como blocos
  concretos.

**Sem migration nova.** O horizonte é calculado on-the-fly
(`max(session.agendada_para)` por regra) — nenhuma coluna `materializadoAte`.

## 3. Arquitetura — 3 camadas (padrão B/C)

### 3.1 Lib pura — `src/lib/agenda/materializar.ts` (+ `.test.ts`)

Sem banco, 100% testável. Opera sobre strings ISO e `Date`.

**`resolverInstante(dataISO: string, horaHHMM: string, fuso: string): Date`** — o
núcleo. Acha o instante absoluto cujo wall-clock em `fuso` é o naive dado.
Algoritmo (inverso de `paraMinutosLocais`, robusto a DST):

```
naiveMs = Date.UTC(ano, mes, dia, hora, min)      // wall-clock interpretado como UTC
ts = naiveMs
repetir 2x:                                        // 2 iterações cobrem a virada de DST
  offset = offsetDaZona(ts, fuso)                  // via Intl.formatToParts naquele instante
  ts = naiveMs - offset
retorna new Date(ts)
```

> Duas iterações são suficientes: a 1ª corrige o grosso do offset; a 2ª estabiliza
> quando `ts` cruzou uma fronteira de DST entre a estimativa e o valor final.
> Nunca usa `FUSO_CLINICA_OFFSET` — é isto que satisfaz inv1.

**`datasDaRegra(regra, deISO, ateISO, bloqueios): string[]`** — enumera as datas
ISO do `diaSemana` da regra dentro de `[max(deISO, vigenciaInicio), min(ateISO, vigenciaFim ?? ∞)]`,
**pulando** datas cobertas por qualquer bloqueio aplicável (o chamador já filtra
os bloqueios por escopo: clínica sempre, terapeuta da regra, paciente da regra).
Aritmética de data em UTC (mesmo padrão de `semana.ts`), sem tocar horário local.

**`ocorrenciasAgendar(regra, datas, fuso): OcorrenciaNova[]`** — mapeia cada data
para `{ agendadaPara: resolverInstante(data, regra.horaInicio, fuso), duracaoMin,
disciplina, ... }`. Combina os dois anteriores para o chamador.

> **F3 (unificação de ancoragem):** `resolverInstante` vira **o único** caminho
> naive→`timestamptz` da agenda. A Etapa C `criarAvulsa` hoje ancora com
> `FUSO_CLINICA_OFFSET` fixo (`...T09:00:00-03:00`); a Etapa D **migra
> `criarAvulsa` para `resolverInstante`** (mesma zona `clinic.timezone`),
> eliminando os dois métodos divergentes. A UI **não** anuncia suporte a
> múltiplos fusos — é higiene interna à prova de futuro, não feature v1.

### 3.2 Queries ctx-accepting — `agenda/queries.ts` (fora de `use server`)

Todas passam por `requireRole(ctx, "coordenador")` + `withTenant(ctx, fn)`.

**`materializarRegra(ctx, regraId, ateISO?): Promise<ResultadoMaterializacao>`**

1. Carrega a regra (do tenant), os bloqueios aplicáveis (clínica + terapeuta +
   paciente da regra) que tocam o intervalo, e `max(session.agendada_para)` da
   regra (o "materializado até" atual).
2. `deISO = max(agendadaParaMax + 1 dia, vigenciaInicio)`;
   `ateISO = ateISO ?? hoje + 12 semanas`.
3. `datas = datasDaRegra(regra, deISO, ateISO, bloqueios)`;
   `ocorrencias = ocorrenciasAgendar(regra, datas, clinic.timezone)`.
4. **Insere ocorrência-por-ocorrência dentro de um savepoint** (drizzle nested
   `tx.transaction()` → `SAVEPOINT`), **sem `onConflictDoNothing`**, capturando o
   SQLSTATE no `catch`:
   - `23505` (unique_violation, `uq_session_recorrente_agendada`) → **skip
     silencioso** (retry idempotente, D-2).
   - `23P01` (exclusion_violation, EXCLUDE gist) → **coleta a data em `puladas[]`**
     (overbook, D-3) e segue.
   - qualquer outro código → **rethrow** (aborta a tx).
     ⚠️ **F1 (crítico) — por que não `onConflictDoNothing`:** (a) `onConflictDoNothing()`
     SEM target arbitra _toda_ constraint — inclusive a EXCLUDE gist — e **engole o
     `23P01` silenciosamente**, matando `puladas[]`. (b) O índice de idempotência é
     **parcial** (`WHERE recorrente_id IS NOT NULL`), então `onConflictDoNothing({target})`
     exigiria casar o predicado parcial no arbiter — frágil. O savepoint capturando
     os dois códigos separa `23505` (skip) de `23P01` (reporta) de forma explícita e
     sem depender de arbiter parcial. O batch não aborta.
5. Retorna `{ geradas: number, puladas: string[] }`. (Sem `materializadoAte` — ver
   F4 em §3.4: o horizonte não é exibido como data única enganosa.)

**`estenderHorizonte(ctx, regraId): Promise<ResultadoMaterializacao>`** — açúcar:
`materializarRegra(ctx, regraId, hoje + 12 semanas)`. Como o `deISO` parte de
`max(agendadaPara)+1dia`, estender só gera o delta (idempotente por construção).

**`contarFuturasDaRegra(ctx, regraId, dataFimISO?): Promise<number>`** — conta as
`session estado='agendada' AND agendada_para > cutoff` **sem deletar**. Alimenta a
confirmação de encerramento (F5): a UI mostra o nº antes do coordenador confirmar.

**`encerrarRegra(ctx, regraId, dataFimISO?): Promise<{ removidas: number }>`**

1. `cutoff = fim do dia de (dataFimISO ?? hoje)` no fuso da clínica. **Fronteira
   travada (F5a):** `cutoff = fim do dia` ⇒ sessões de **hoje ficam**; deleta de
   **amanhã** em diante.
2. `UPDATE agendamento_recorrente SET status='encerrado', vigencia_fim = date(cutoff)`.
3. `DELETE FROM session WHERE recorrente_id = regraId AND estado='agendada' AND agendada_para > cutoff`
   — **só futuras agendadas**; `realizada`/`falta`/`cancelada` preservadas (inv3).
   Ocorrência futura `agendada` não tem filhos (`session_note`/`audio`/`extraction`
   só existem pós-atendimento) → DELETE sem órfão de FK.
4. Retorna `{ removidas }`. Trocar horário no meio do tratamento = `encerrarRegra`
   - `criarRegra` nova (compõe Etapa C; o alvo vive em `patient_alvo_disciplina`,
     não duplica — spec mestre inv3).

**`proximaSessaoDaRegra(ctx, regraId): Promise<string | null>`** —
`min(agendada_para) WHERE agendada_para > now()`, para a UI mostrar **"próxima
sessão: DD/MM"** (F4). Substitui o antigo "materializado até": grandeza sempre
verdadeira, ao contrário de `max(agendada_para)` que subestima cobertura quando a
cauda do horizonte cai em bloqueio.

### 3.3 `criarRegra` (Etapa C) — modificada

Após inserir a regra, chama a materialização inicial **na mesma transação**
(atômico: regra + 12 semanas commitam juntas ou nada; o skip de `23P01` é por
savepoint, não aborta a tx). C1 deixa de ser "0 sessions" e passa a "regra + N
ocorrências materializadas" — o **teste de integração C1 existente é ajustado**
(de `toHaveLength(0)` para asserção do nº de ocorrências no horizonte).

### 3.4 Actions + UI mínima — `agenda/semana/actions.ts` + calendário

- `/agenda/semana`, requisitos de UX (derivados dos achados F2/F4/F5):
  - **F4 — rótulo honesto:** no card/detalhe da regra, **"próxima sessão: DD/MM"**
    (não "materializado até"). O botão **"Estender +12 semanas"** declara o alvo no
    próprio rótulo/resultado (_"agenda garantida até DD/MM"_), sem badge de data
    única enganosa.
  - **F2 — buraco visível e permanente:** as `puladas[]` **não** vivem só num
    toast. A semana pulada aparece marcada no calendário (célula "conflito — não
    agendado") **e** listada de forma persistente no detalhe da regra ("N datas
    não criadas por conflito"). O coordenador resolve ou aceita conscientemente —
    ausência silenciosa é proibida.
  - **F5 — confirmação destrutiva com números:** "Encerrar (esta e futuras)" abre
    confirmação que mostra a contagem real (`contarFuturasDaRegra`): _"Remove N
    sessões futuras (a partir de amanhã). As de hoje e o histórico ficam."_ Nunca
    clique no escuro.
- `estenderAction`, `encerrarRegraAction` — finas (`useActionState`), gate
  coordenador, traduzem `ConflitoError`/`RoleError` em `EstadoAcao`, chamam
  `revalidatePath`. Reusa exclusivamente `src/components/ui/*` (nada hardcoded).

## 4. Invariantes (rastreiam o design mestre §4)

| #    | Invariante Etapa D                           | Mecanismo                                                                                       |
| ---- | -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| D-1  | Materialização IANA (nunca offset congelado) | `resolverInstante` via `Intl` na zona `clinic.timezone`                                         |
| D-2  | Idempotente (retry não duplica)              | savepoint; `catch 23505` → skip silencioso (não `onConflictDoNothing` — índice parcial, ver F1) |
| D-3  | Duplo-book não materializa por cima          | insert por savepoint; `23P01` → pula + reporta em `puladas[]` **persistente na UI (F2)**        |
| D-4  | Pula datas bloqueadas do escopo              | `datasDaRegra` filtra clínica+terapeuta+paciente                                                |
| D-5  | "Esta e futuras" preserva passado            | `DELETE ... estado='agendada' AND agendada_para > cutoff`                                       |
| D-6  | Horizonte rolling on-demand, sem cron        | `max(agendada_para)` + `estenderHorizonte`                                                      |
| D-7  | Atômico na criação                           | materialização na mesma tx do insert da regra                                                   |
| D-8  | Ancoragem naive→instante unificada           | `criarAvulsa` migra p/ `resolverInstante` (F3)                                                  |
| D-9  | Rótulo honesto de cobertura                  | "próxima sessão" (`min`) em vez de "materializado até" (`max`) (F4)                             |
| D-10 | Encerramento com confirmação numérica        | `contarFuturasDaRegra` antes do DELETE (F5)                                                     |

## 5. Testes (mapeiam spec mestre §8)

- **Unit `resolverInstante`:** naive SP → instante UTC correto; **teste DST
  dedicado com `America/New_York`** materializando através da virada (spring
  forward / fall back) provando que o slot não desloca — SP não tem DST hoje,
  NY prova a portabilidade exigida por inv1/§8.
- **Unit `datasDaRegra`:** respeita `[vigenciaInicio, vigenciaFim]`; pula datas
  de bloqueio (borda inclusiva `[dataInicio, dataFim]`); dia-da-semana correto.
- **Integração `materializarRegra`:** roda 2× → nº de sessions estável
  (idempotência D-2); avulsa pré-existente no slot → aquela data em `puladas` e
  o resto materializa (D-3); bloqueio de paciente cobre a semana → aquela
  ocorrência ausente (D-4).
- **Integração `encerrarRegra`:** sessão passada `realizada` preservada, futura
  `agendada` removida, `status='encerrado'` + `vigencia_fim` setada (D-5).
- **Integração `criarRegra` (ajuste C1):** cria regra **e** as ocorrências do
  horizonte na mesma tx (D-7).
- **Integração atomicidade (F5b):** (a) erro **não-`23P01`** no meio da
  materialização de `criarRegra` reverte a **regra inteira** (0 linhas em ambas
  as tabelas); (b) `23P01` numa ocorrência da materialização inicial **não**
  aborta o insert da regra (regra criada, aquela data em `puladas`).
- **Integração F1 (regressão):** avulsa no slot → a colisão aparece em `puladas`
  (guarda contra `onConflictDoNothing` sem target, que a esconderia).
- **Integração `criarAvulsa` pós-F3:** ancoragem via `resolverInstante` produz o
  mesmo `agendada_para` que o offset fixo produzia para SP (não-regressão).
- **RLS/IDOR:** as novas queries isolam por tenant; regra de outra clínica não
  materializa nem encerra.
- **a11y:** axe (`wcag2a/aa`, `color-contrast` religado) nos controles novos.

## 6. Decisões travadas nesta sessão

| #         | Decisão                                                                                                                                                                                                                       |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DD1       | Materialização roda em `criarRegra` (auto, horizonte inicial 12sem) + botão "estender". Não é ação puramente manual.                                                                                                          |
| DD2       | Ponto de retomada da materialização calculado on-the-fly via `max(session.agendada_para)` por regra — **sem** coluna nova, sem migration. (É lógica interna de "de onde continuo"; a UI **não** exibe esse `max` — ver DD11.) |
| DD3       | Colisão EXCLUDE (`23P01`) na materialização → **pula a ocorrência e reporta** em `puladas[]`; nunca aborta o batch.                                                                                                           |
| DD4       | Etapa D entrega lib + queries + actions + **UI mínima** (próxima-sessão, estender, encerrar) — ponta a ponta, padrão B/C.                                                                                                     |
| DD5       | `criarRegra` + materialização inicial = **mesma transação** (atômico); skip de `23P01` via savepoint por insert (drizzle nested tx).                                                                                          |
| DD6       | "Esta e futuras": cutoff = fim do dia `dataFim` (ou hoje); deleta só `session estado='agendada' AND agendada_para > cutoff`.                                                                                                  |
| DD7       | Trocar horário = `encerrarRegra` + `criarRegra` nova (compõe Etapa C); alvo separado em `patient_alvo_disciplina` não duplica.                                                                                                |
| DD8 (F1)  | Skip via **savepoint capturando SQLSTATE** (`23505`→skip, `23P01`→`puladas`, outro→rethrow), **não** `onConflictDoNothing` — este engoliria o `23P01` e o índice de idempotência é parcial (arbiter frágil).                  |
| DD9 (F2)  | `puladas[]` tem superfície **persistente** (célula no calendário + lista no card da regra), não só toast.                                                                                                                     |
| DD10 (F3) | `resolverInstante` é o único caminho naive→instante; `criarAvulsa` (Etapa C) migra p/ ele. UI não anuncia multi-fuso.                                                                                                         |
| DD11 (F4) | UI mostra **"próxima sessão"** (`min > now`), não "materializado até" (`max`) — este subestima cobertura com cauda bloqueada.                                                                                                 |
| DD12 (F5) | Encerrar mostra **contagem** (`contarFuturasDaRegra`) antes de confirmar; fronteira travada: hoje fica, amanhã+ sai.                                                                                                          |

## 7. Riscos residuais

- **`resolverInstante` e DST:** a correção de 2 iterações é o ponto mais sutil.
  Mitigado pelo teste DST com NY. Horários "inexistentes" (spring-forward gap)
  ou "ambíguos" (fall-back overlap) não ocorrem em SP hoje; o comportamento em
  NY nesses casos é documentado no teste, não é caminho de produção da clínica.
- **Custo do skip por savepoint:** um savepoint por ocorrência (≤ ~12–14 por
  materialização de 12 semanas) é barato; não há N+1 de rede relevante.
- **Regra sem fim (`vigenciaFim` null):** `datasDaRegra` limita sempre pelo
  `ateISO` (horizonte), então nunca gera infinito; o rolling depende do
  "estender" manual (dívida de cron mantida, spec mestre §2).
