## 4A — Evidence layer

### 4A.1 Enum + tabelas (Drizzle → `0013`)

- `evidence_revision_acao` enum: `confirmar | reclassificar | invalidar`.
- `evidence` — **grão de alvo** (1 linha = 1 `alvos[]`), com `protocol_id` explícito e
  `UNIQUE NULLS NOT DISTINCT (extraction_id, goal_id, milestone_id)`. `REVOKE UPDATE, DELETE`.
- `evidence_revision` — append-only; `autor_id` sempre coordenador (app garante + RLS).
- `evidence_query` — "devolver com dúvida" (V2); FK opcional para a `evidence_revision` resultante.
- View `evidence_current` **`WITH (security_invoker = true, security_barrier = true)`**.

(DDL exata já reconciliada em `modelo-de-dados.md` §2.2 — esta spec não a duplica; referencia.)

### 4A.2 RLS (SQL à mão → `0014`), modelado nos padrões existentes

```
-- evidence: leitura clínica (coordenador toda a clínica; terapeuta da equipe).
ALTER TABLE evidence ENABLE ROW LEVEL SECURITY;
ALTER TABLE evidence FORCE ROW LEVEL SECURITY;
GRANT SELECT, INSERT ON evidence TO app_role;          -- UPDATE/DELETE já revogados
CREATE POLICY evidence_select ON evidence FOR SELECT TO app_role USING (
  app_patient_in_clinic(patient_id)
  AND (current_setting('app.user_role') = 'coordenador' OR app_is_on_team(patient_id))
);
-- INSERT no momento da aprovação da extração: terapeuta dono da sessão OU coordenador.
CREATE POLICY evidence_insert ON evidence FOR INSERT TO app_role WITH CHECK (
  app_patient_in_clinic(patient_id)
  AND (current_setting('app.user_role') = 'coordenador' OR app_is_on_team(patient_id))
);

-- evidence_revision / evidence_query: escrita restrita ao coordenador (governança V1/V2).
--   select: mesma visibilidade clínica via join lógico a evidence.patient_id.
--   insert: current_setting('app.user_role') = 'coordenador'.
-- (exceção: a RESPOSTA de uma EvidenceQuery gera evidence_revision de autoria do TERAPEUTA —
--  ver §4A.4; policy de insert de revision aceita coordenador OU terapeuta-da-equipe COM
--  evidence_query aberta apontando pra evidência; app valida o vínculo.)
```

> ⚠️ **Teste obrigatório (DoD):** `SELECT` cross-tenant **através de `evidence_current`** retorna 0
> linhas. O teste na tabela base não cobre a view (B2). Adicionar a `rls.int.test.ts`.

### 4A.3 Backfill (D2) — `scripts/backfill-evidence.ts`, idempotente

- Fonte: `extraction` com `estado ∈ {aprovada, editada}` (exclui `descartada`, `sugerida`,
  `pendente_reprocessamento`).
- Para cada extração: explode `alvos[]` do `payloadEditado ?? payload` → 1 `evidence` por alvo,
  com `protocol_id`, `goal_id`, `milestone_id` do alvo, `classificacao_original` = o alvo aprovado.
- **Pré-condições / skips:**
  - `session.numero_sequencial_paciente IS NULL` → **pular** (evidence.session_numero é NOT NULL;
    número só existe após consolidação).
  - `estado = 'editada'` com `payloadEditado IS NULL` → **rejeitar com erro** (inconsistência).
- Idempotência: `ON CONFLICT ON CONSTRAINT uq_evidence_alvo DO NOTHING`.
- Roda primeiro em local/seed e na **clínica demo** antes de qualquer coisa perto de dado real;
  execução em prod é passo manual "confirmar antes".
- **Rollback:** como é idempotente e só INSERT, rollback = `DELETE FROM evidence WHERE ...` por
  lote de backfill (registrar `extraction_id`s tocados); documentar no runbook do script.

### 4A.4 Efeito colateral: R14 destrava

Com `evidence` real, `historico_relevante` do agente passa a ser projetado de
`session_snapshot.repertorio_state` (4B) — **não** de `segmentacao`. Até 4B existir, R14 segue
lendo extração aprovada (comportamento atual). Nenhuma mudança em `output-schema.json`.

## 4B — SessionSnapshot & candidatura

### 4B.1 Tabela (Drizzle → `0015`)

`session_snapshot` conforme `modelo-de-dados.md` §2.5 reconciliado:
`repertorio_state` (numérico/enum), `segmentacao` `{goal_id:{protocol_id:{tipo_estrutura,metrica,rotulo}}}`,
PK `(patient_id, session_numero)`.

### 4B.2 RLS (→ `0016`)

- Leitura: espelha `milestone_candidacy_select` (`app_patient_in_clinic(patient_id)` + coordenador/
  equipe). Sem `clinic_id` (padrão FK-a-paciente, igual candidacy).
- **Escrita: NENHUMA policy para `app_role`** — só a função definer escreve (ver 4B.3). `GRANT
SELECT` a `app_role`; sem `GRANT INSERT/UPDATE`.

### 4B.3 Materialização via `SECURITY DEFINER` (D1)

```
CREATE FUNCTION app_materializar_snapshot(p_patient uuid, p_desde_numero int)
  RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
BEGIN
  PERFORM pg_advisory_xact_lock(hashtextextended(p_patient::text, 0));  -- serializa por paciente
  -- recomputa session_snapshot de p_desde_numero em diante:
  --   snapshot(n) = snapshot(n-1) + fold das evidences(sessão n), em grão de alvo,
  --   resolvendo protocol_id da coluna; segmentação despacha por Milestone.tipo_estrutura.
  -- recomputa milestone_candidacy / goal_candidacy afetadas (§4B.4).
  -- NUNCA toca evidence/evidence_revision (log imutável) nem MilestoneAssessment (V3, Fase 5).
END; $$;
REVOKE ALL ON FUNCTION app_materializar_snapshot(uuid,int) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION app_materializar_snapshot(uuid,int) TO app_role;
```

- Chamada **síncrona** logo após: (a) aprovação de extração → evidências novas; (b) reclassificação/
  invalidação de evidência (coordenador) → recompute retroativo de `session_numero` afetado em
  diante. A definer contorna o gate de papel (candidatura é `coordenador`-only) de forma controlada.
- Definer roda como dono (bypass RLS): a função **filtra explicitamente por `p_patient`** e é a
  única porta de escrita — não recebe input de outra clínica porque o chamador só passa pacientes
  que já leu sob RLS.

### 4B.4 Candidatura — reativação com critério por Milestone/família (correção protocolar)

- `milestone_candidacy`: **não** usar `N=3/M=2` global. Critério vem de `Milestone.estrutura`
  (VB-MAPP: critério embutido no marco). Famílias naturalistas (Denver/ESDM) exigem dimensão de
  **generalização** (R12 já captura) — não só contagem. Famílias de **observação (PROC/ABFW)** não
  usam candidatura por acúmulo → marcar como não-candidatáveis por essa via.
- `goal_candidacy`: via `Goal.criterio_dominio` (JSONB) — avaliador genérico que lê o tipo
  (`sessoes_consecutivas_independente`, etc.), sem interrupção por negativa (anti cherry-picking).
- **Evidência com `evidence_query` aberta (aguardando terapeuta) NÃO conta** em candidatura até
  resolvida (V1e).

### 4B.5 Segmentação — função determinística despacha por `tipo_estrutura`

`marco_simples` → ordinal `nivel_ajuda`; `marco_com_barreira` → escore barreira (invertido);
`escore_composto` → escore composto; `faixa_normativa` → idade-equiv. relativa à cronológica.
Nunca cruza ordinais entre protocolos. Testes: 1 por `tipo_estrutura` + caso multi-família
(Caso 9 de `casos-de-teste.md`).
