## 0. Pré-condição — Etapa A concluída

Auditoria em código confirma Etapa A 100% implementada: schema
(`src/db/schema.ts`), migrations `0021`–`0035` (tabelas novas, `btree_gist`,
EXCLUDE gist anti-overbook, enum `session_estado` recriado, FKs compostas,
RLS `WITH CHECK`), alvo-por-disciplina gravado na mesma transação do cadastro
de paciente, e 9 arquivos de teste de integração. **Etapa B não toca DDL** —
as tabelas `janela_trabalho` e `bloqueio` já existem no banco. B é a camada
de **UI + server actions + rota nova do terapeuta**.

## 1. Escopo

### Entrega
- Editor de disponibilidade do terapeuta (grava `janela_trabalho`).
- Bloqueios nos 3 escopos (`bloqueio`): terapeuta, paciente, clínica.
- Rota nova `/equipe/[id]` (perfil-base do terapeuta) com **capacidade/sem**.
- Aba **Ausências** no perfil do paciente (`/pacientes/[id]`).
- Seção mínima **Clínica → Feriados** (casa do bloqueio escopo=clínica).

### Adia (dívida explícita, registrada no BACKLOG)
- **Alocado/vago** e **lista de pacientes fixos** no perfil do terapeuta —
  dependem de regras (`agendamento_recorrente`) e sessões → Etapa F.
- Materialização de ocorrências → Etapa D.
- Calendário semanal e alocação → Etapa C.
- Indicador "de férias esta semana" no perfil → Etapa F (junto de vago).

## 2. Decisões desta sessão

| # | Decisão |
| --- | --- |
| B1 | Perfil do terapeuta em B mostra **"disponibilidade oferecida/sem" (espaço)** = Σ janelas ÷ 60. **Não** é carga/capacidade de trabalho: hora do terapeuta é relação com a **empresa (RH)**, fora do escopo do Iris — o Iris só oferece o espaço a preencher. Alocado/vago → F |
| B2 | Bloqueio de **paciente** mora no perfil do paciente (aba Ausências); de **terapeuta** no `/equipe/[id]`; de **clínica** em Clínica → Feriados |
| **D3-revisada** | Editor de disponibilidade = **grade visual** (drag no mouse/touch + teclado). Revisando a D3 original (selects de hora). Motivo do OK: o produto é testado com **touch + teclado**, os dois inputs que a grade precisa; drag em touch é natural. Requisito: teclado operável + `color-contrast` habilitado no axe da grade (ver §9) |
| B3 | Escopo=clínica ganha casa mínima agora (Clínica → Feriados), não é adiado |

| B5 | Etapa B **não consome `clinic.timezone`** (janelas são hora "crua", sem materialização). Unificação de fuso (uma fonte só) é dono da **Etapa D**. Evita criar a "segunda verdade de fuso" |

## 3. Dados — sem DDL nova; server actions + invariantes

Nenhuma migration nova. B adiciona server actions e uma query derivada.
Invariantes que o coordenador exige e o design mãe não escreveu:

- **I-B1 — faixas não sobrepõem:** ao salvar as janelas de um dia, faixas
  sobrepostas ou encostadas (`horaFim` de uma == `horaInicio` da seguinte)
  **fundem** numa só (08–12 + 10–14 → 08–14; 08–12 + 12–17 → 08–17). Senão o
  "espaço oferecido/sem" conta hora dobrada. **Invariante de app + teste
  unitário** (lógica pura) — sem constraint gist no banco: stakes baixos (só
  suja o número de espaço, não causa overbook; o EXCLUDE de `session` da
  Etapa A já protege o overbook real). Proporcional.
- **I-B2 — só coordenador edita** disponibilidade e bloqueio. **A RLS já é a
  fronteira** (bloqueia terapeuta escrevendo `janela_trabalho` — provado em
  `db/tests/agenda2-janela-trabalho-rls.int.test.ts:89`). O `requireRole` na
  action é **defesa-em-profundidade + erro amigável**, não a única trava.
  Disciplina real de segurança: **todo caminho de leitura novo** (query de
  espaço/sem, `/equipe/[id]`, lista de terapeutas) **passa por `withTenant`** —
  sem os GUCs `app.*` a RLS nega tudo. Terapeuta vê o próprio perfil em leitura.
- **I-B3 — snap a `passoGradeMin`** (default 30 na clínica): a grade pinta em
  blocos de `passoGradeMin`; `horaInicio`/`horaFim` salvos são sempre
  múltiplos do passo.
- **I-B4 — `horaFim > horaInicio`** por faixa (design mãe §3.3; a grade
  garante por construção, a action revalida).
- **I-B5 — bloqueio `dataFim >= dataInicio`**; escopo casa com o id
  obrigatório (escopo=terapeuta ⇒ `terapeutaId`; escopo=paciente ⇒
  `patientId`; escopo=clínica ⇒ ambos null). Já é a forma da tabela; a action
  valida antes de inserir.

## 4. Superfícies e arquitetura de informação

| Rota / lugar | Conteúdo | Observações |
| --- | --- | --- |
| `/equipe` **(nova lista)** | lista de terapeutas da clínica com link p/ o perfil | **sem isso a rota `[id]` fica inalcançável** (hoje só existe `/equipe/convidar`). Read via `withTenant` |
| `/equipe/[id]` **(nova)** | header do terapeuta (nome, papel) · **disponibilidade oferecida/sem** · editor de janelas · lista de bloqueios do terapeuta | empty-state se sem janela (CTA "configurar disponibilidade"). Edição só coordenador (I-B2). `params: Promise<{id}>` (Next 16) |
| `/pacientes/[id]` → aba **Ausências** | bloqueios escopo=paciente (férias/viagem) | mata a falta-fantasma que dispararia "abaixo do prescrito" |
| **Clínica → Feriados** (seção mínima nova) | bloqueios escopo=clínica (lista + adicionar intervalo + motivo) | registro único vale para todos; feriado nacional. Escopo travado — ver §8 |

**Uma engrenagem só (I-B5) atrás das 3 telas de ausência:** uma única server
action escopo-discriminada (terapeuta/paciente/clínica) com uma validação de
coerência escopo↔id, não três cópias divergentes. Cada superfície reusa o
padrão server action + `useActionState` + `withTenant` das fases anteriores
(`novo-paciente-form.tsx`). Componentes de calendário/alocação **não** entram
aqui (Etapa C).

## 5. Grade de disponibilidade (a11y-first)

- Estrutura: `role="grid"`, 7 linhas (dom→sáb) × colunas de largura
  `passoGradeMin`, cobrindo a faixa de horas útil da clínica.
- Célula = toggle "trabalha / não trabalha".
- **Teclado (requisito):** setas navegam a grade; Enter/Espaço alterna a
  célula focada; Shift+seta pinta em faixa contínua. Cada célula anuncia dia +
  intervalo + estado ao leitor de tela.
- **Drag (mouse E touch):** enhancement sobre o mesmo modelo de mutação. O
  produto é testado com touch + teclado, então os dois caminhos são exercitados
  de fato; drag em touch é o argumento a favor da grade vs a listinha.
- **"Copiar dia":** botão que replica as faixas de um dia (ex. segunda) para
  os demais dias úteis — a dor real do coordenador é montar 5 dias idênticos.
- Persistência: as células pintadas de cada dia viram faixas contíguas
  (`janela_trabalho`), aplicando I-B1 (fusão) no salvamento. Sáb/dom vazios
  por default.

## 6. Cálculo exposto em B

- **Disponibilidade oferecida/sem** = Σ (`horaFim` − `horaInicio`) das janelas
  (já fundidas por I-B1) ÷ 60. Derivado, sem denormalizar. **Não** é carga do
  terapeuta (isso é RH, fora do Iris) — é quanto espaço ele abre para alocação.
  Bloqueios **não** entram aqui; desconto de bloqueio compõe *vago* (Etapa F).
- O teto de **40h/sem do paciente** (soma de terapia por disciplina) é métrica
  de **paciente**, calculada na Etapa F — não aparece em B.

## 7. Testes

- **Unit (lógica pura):** fusão de faixas (I-B1, encostadas e sobrepostas
  parciais), soma de disponibilidade/sem, snap a `passoGradeMin`.
- **Integração (com Postgres):** `requireRole` como defesa-em-profundidade nas
  actions de janela e bloqueio; validação de coerência escopo↔id do bloqueio
  (I-B5); **todo read novo dentro de `withTenant`** (RLS de tenant já coberta na
  Etapa A é a fronteira).
- **a11y:** grade de disponibilidade, `/equipe` (lista), `/equipe/[id]`, aba
  Ausências, Feriados. **A grade re-habilita `color-contrast` no axe** (o
  harness padrão o desliga — `agenda/a11y.test.tsx:28-33` — então um novo
  componente visual passaria verde sem checar contraste). Axe é estático:
  **operabilidade por teclado é testada por interação** (`fireEvent`/
  `user-event`), não por axe. 1 passada manual de leitor de tela.

## 8. Riscos residuais

- **a11y ao longo do tempo — eixo leitor de tela:** touch + teclado são
  exercitados pelo teste manual do dev; leitor de tela não. Mitigação barata já
  no plano (contraste no axe da grade + interação de teclado + 1 passada manual
  de leitor). Este é o único resíduo real da etapa.
- **Editar janela depois:** em B não há sessões (vêm em C), e sessões nunca
  referenciam `janela_trabalho` (materializam de `agendamento_recorrente`).
  Então encolher janela é seguro; a coerência "regra dentro da janela" é
  preocupação da Etapa C, não de B.
- **Seção Feriados mínima:** enxuta de propósito; escopo travado (lista +
  intervalo + motivo, sem recorrência anual nem gestão de admin na v1). Se a
  clínica ganhar config ampla depois, Feriados migra sem mudar o dado.
- **Fuso:** B não lê `clinic.timezone` (B5); a unificação de fonte única de
  fuso é responsabilidade explícita da Etapa D. Não criar a segunda verdade.
