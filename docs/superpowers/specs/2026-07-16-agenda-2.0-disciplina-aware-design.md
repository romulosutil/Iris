# Agenda 2.0 — jornada disciplina-aware (design)

> Data: 2026-07-16 · Status: **aprovado para virar plano de implementação**
> Origem: redesign da criação de agenda (fluxo atual pede UUID cru; jornada
> nova é select-first, calendário semanal, recorrência e métricas de horas).
> Validado por revisão adversarial (Tech Lead + Coordenador de terapias).

## 1. Problema e objetivo

O fluxo de agendamento atual (`src/app/(app)/agenda/agendar-form.tsx`) pede
`patientId` e `terapeutaId` como **UUID digitado à mão** + `datetime-local`.
É frágil (typo só falha no banco), não tem noção de disponibilidade, carga
horária, recorrência nem ocupação do terapeuta.

Objetivo: uma jornada homogênea, **select-first**, em que o coordenador
configura a disponibilidade do terapeuta, monta a semana num **calendário
visual**, aloca pacientes por nome, repete a configuração por N semanas, e
enxerga carga horária tanto no perfil do paciente quanto no do terapeuta.

O ponto central descoberto na revisão: o atendimento é **multidisciplinar**
(o schema já expõe `care_team_membership.disciplina`). O átomo do modelo tem
que ser *disciplina-aware*, com **duração variável por disciplina**, **sessão
com estado** e **visão por paciente** — não só por terapeuta.

## 2. Escopo

### Reusa (não reescreve)
- Cadastro de paciente (`/pacientes/novo`, funcional — inclui consent LGPD).
- Convite/onboarding de terapeuta (`/equipe/convidar` + `provisionUser`).
- Perfil de paciente (`/pacientes/[id]`, abas Evolução/Briefing/Metas/…).
- Tabela `session`, padrão RLS multi-tenant `WITH CHECK`, `FUSO_CLINICA`.

### Adiciona
- Disponibilidade (`janela_trabalho`) e bloqueios (`bloqueio`).
- Alvo de carga horária **por disciplina, com vigência** (`patient_alvo_disciplina`).
- Recorrência standing (`agendamento_recorrente`).
- Enriquecimento de `session` (disciplina, duração, estado, reposição,
  atendido-por, modalidade, tipo).
- Calendário semanal com **duas visões** (por terapeuta e por paciente).
- Perfil de terapeuta (nova rota `/equipe/[id]`).
- Select-por-nome de paciente/terapeuta (mata o UUID cru).

### Fora da v1 — dívida explícita (registrada no BACKLOG)
- **Grupo / co-terapia** (1 sessão N pacientes; 1 paciente N terapeutas). A
  clínica faz *raramente*: v1 fica **1 sessão = 1 paciente = 1 terapeuta**,
  migração aceita conscientemente quando entrar.
- Lista de espera / encaixe de vagas.
- Cron automático de materialização (v1 é on-demand).
- Exceções de janela mais finas que bloqueio-por-data.
- **Regras de faturamento** (competência/prazo de reposição, glosa por falta
  não justificada): o *dado* é modelado na v1; a *lógica* fica para depois.

## 3. Modelo de dados

Todas as tabelas novas carregam `clinicId` e política RLS `WITH CHECK` no
padrão das fases anteriores. Anti-IDOR (campo sob controle do coordenador):
**paciente** usa **FK composta `(patientId, clinicId)`** → exige `UNIQUE
(patient.id, clinicId)`. **Terapeuta** *não* pode usar FK composta — `app_user`
é a tabela global do Better-Auth e **não tem `clinicId`** (o vínculo é via
`user_role`); então o tenant do terapeuta é validado por `app_user_in_clinic()`
no `WITH CHECK`, exatamente como o `session` já faz hoje.

### 3.1 Ajustes em tabelas existentes

```
clinic
  + timezone            text        # zona IANA, ex "America/Sao_Paulo" (materialização correta / DST)
  + passoGradeMin       int  = 30   # granularidade visual do calendário
  + duracaoDisciplina   jsonb       # default de duração por disciplina, ex {"aba":60,"fono":30,"to":50}

patient
  (sem coluna nova — alvo vai em tabela própria com vigência, ver 3.2)
```

### 3.2 `patient_alvo_disciplina` (NOVA) — alvo contratado, auditável

```
id            uuid pk
clinicId      uuid → clinic
patientId     uuid  (FK composta (patientId, clinicId) → patient)
disciplina    text                 # "aba" | "fono" | "to" | "psicologia" | ...
horasAlvoSemana numeric(4,1)        # ex 12.0
vigenciaInicio  date
vigenciaFim     date null           # null = vigente
criadoEm      timestamptz = now()
```

> Vigência é obrigatória porque prescrição muda no meio do tratamento (2h→4h
> de ABA) e o convênio audita o alvo **da época**, não o de hoje.

### 3.3 `janela_trabalho` (NOVA) — disponibilidade do terapeuta

```
id            uuid pk
clinicId      uuid → clinic
terapeutaId   uuid  → app_user (papel terapeuta; anti-IDOR via app_user_in_clinic() no WITH CHECK — ver nota abaixo)
diaSemana     smallint             # 0=domingo … 6=sábado
horaInicio    time
horaFim       time                 # > horaInicio
criadoEm      timestamptz = now()
```

Várias faixas por dia permitidas (manhã + tarde). Default sugerido na UI:
seg-sex; sábado é faixa **opcional**. Sem exceções finas na v1 (isso é
`bloqueio`).

### 3.4 `bloqueio` (NOVA) — feriado / férias / afastamento (polimórfico)

```
id            uuid pk
clinicId      uuid → clinic
escopo        enum(clinica, terapeuta, paciente)
terapeutaId   uuid null  (FK composta; obrigatório se escopo=terapeuta)
patientId     uuid null  (FK composta; obrigatório se escopo=paciente)
dataInicio    date
dataFim       date                 # intervalo inclusivo
motivo        text
criadoEm      timestamptz = now()
```

> Bloqueio de **paciente** (férias/viagem da criança) é obrigatório na v1:
> sem ele, a criança viajando 3 semanas gera "falta" fantasma e dispara o
> alerta "abaixo do prescrito" indevidamente. A materialização pula datas
> bloqueadas (do escopo aplicável) e o cálculo de horas vagas as desconta.

### 3.5 `agendamento_recorrente` (NOVA) — a regra standing

```
id            uuid pk
clinicId      uuid → clinic
patientId     uuid  (FK composta (patientId, clinicId) → patient)
terapeutaId   uuid  → app_user (anti-IDOR via app_user_in_clinic(), ver 3.3)
disciplina    text
diaSemana     smallint
horaInicio    time
duracaoMin    int                  # herda default da disciplina, editável
vigenciaInicio date
vigenciaFim    date null            # null = indefinido
status        enum(ativo, encerrado)
criadoEm      timestamptz = now()
```

Um paciente tem **N regras** (uma por disciplina/terapeuta/horário) — é assim
que a criança de 3 terapeutas é representada.

### 3.6 `session` — enriquecida

```
session (existente)
  + recorrenteId   uuid null → agendamento_recorrente   # null = avulsa
  + disciplina     text
  + duracaoMin     int  NOT NULL DEFAULT 60   # legado recebe 60; app grava o default da disciplina
  + estado         enum(agendada, realizada, falta_paciente, falta_terapeuta, cancelada)
                                                          # substitui/expande o enum atual
  + justificada    boolean null      # só relevante em falta_*; base p/ regra de glosa futura
  + modalidade     enum(presencial, online) = presencial
  + tipo           enum(terapia, avaliacao, devolutiva, reuniao_pais, outro) = terapia
  + atendidoPorId  uuid null → app_user (anti-IDOR via app_user_in_clinic())  # quem REALMENTE atendeu (substituto)
  + repostaDe      uuid null → session                   # se esta sessão repõe outra (makeup)

  UNIQUE (recorrenteId, agendadaPara)                    # materialização idempotente
  EXCLUDE USING gist (                                    # anti duplo-book (requer btree_gist)
     terapeutaId WITH =,
     tstzrange(agendadaPara, agendadaPara + duracaoMin * interval '1 min') WITH &&
  ) WHERE (estado = 'agendada')
  -- constraint análoga para patientId
```

Notas:
- `atendidoPorId` null ⇒ atendeu o `terapeutaId` previsto. Preenchido quando um
  substituto cobre o slot — o convênio precisa saber quem atendeu, sem quebrar
  a regra original.
- `tipo` + `recorrenteId null` cobrem **sessão avulsa** (avaliação inicial,
  devolutiva, reunião de pais) — não são recorrentes e precisam existir na v1.
- O EXCLUDE só vale para `estado='agendada'`: sessão cancelada/falta libera o
  horário para novo agendamento.

## 4. Regras de consistência (invariantes)

1. **Materialização via IANA:** ocorrências são geradas resolvendo `horaInicio`
   (naive) na zona `clinic.timezone` **no momento da geração**, nunca com offset
   fixo congelado — senão a virada de horário de verão desloca o slot 1h.
2. **Duplo-book garantido no banco** (EXCLUDE gist), não só em app-check: dois
   coordenadores alocando o mesmo slot em paralelo é TOCTOU; o OCC (`versao`,
   fase 4) protege edição de *uma* linha, não colisão de *duas linhas novas*.
3. **Editar/encerrar regra = "esta e futuras":** fecha `vigenciaFim` da regra e
   remove/reagenda apenas `session` **futuras com `estado='agendada'`**;
   sessões passadas (realizada/falta) são preservadas como histórico. Trocar
   horário no meio do tratamento = encerrar a regra antiga + abrir nova; o alvo
   vive em `patient_alvo_disciplina` (separado das regras), então **não
   duplica**.
4. **Materialização rolling on-demand:** ao criar a regra ou clicar "estender",
   gera ocorrências até um horizonte (default 12 semanas). A tela mostra
   "agenda materializada até DD/MM" + alerta para não abrir buraco. Idempotente
   via `UNIQUE(recorrenteId, agendadaPara)` (retry não duplica). Cron fica
   deferido.
5. **Realizado por semanas ativas:** aderência = sessões `realizada` ÷ semanas
   **desde a 1ª sessão da disciplina** (não ÷ janela fixa) — paciente novo não
   aparece com 25% falso. Calculado **por disciplina**.
6. **LGPD:** alocação só após consent do paciente (já é pré-requisito do
   cadastro; manter o gate).

## 5. Cálculos de carga horária

Todos derivados; nada denormalizado além do alvo.

| Métrica | Fórmula |
| --- | --- |
| Paciente — **agendado**/sem (por disciplina) | Σ `duracaoMin` das regras ativas da disciplina ÷ 60 |
| Paciente — **alvo**/sem (por disciplina) | `patient_alvo_disciplina.horasAlvoSemana` vigente |
| Paciente — **realizado**/sem (por disciplina) | média de `duracaoMin` de sessões `realizada` por semana ativa |
| Paciente — **defasagem** | alvo − agendado; alerta se agendado < alvo por ≥ 2 semanas consecutivas (limiar configurável) |
| Terapeuta — **capacidade**/sem | Σ (`horaFim` − `horaInicio`) das janelas ÷ 60 |
| Terapeuta — **alocado**/sem | Σ `duracaoMin` das regras ativas ÷ 60 |
| Terapeuta — **vago**/sem | capacidade − alocado − bloqueios do período |

## 6. Jornada e telas

1. **Configurar disponibilidade** (coordenador, no perfil do terapeuta):
   grade semanal, marca faixas por dia com selects de hora início/fim
   (seg-sex default, sábado opcional). Grava `janela_trabalho`. Registra
   bloqueios (feriado/férias) na mesma área.
2. **Calendário semanal** (nova tela, ex. `/agenda/semana`): seletor de
   **terapeuta por nome**; grade renderiza faixas de trabalho e pinta slots
   *livre / ocupado / fora-da-janela / bloqueado*. Grade de referência a cada
   `passoGradeMin`; sessões posicionadas/dimensionadas pelo horário+`duracaoMin`
   exatos.
3. **Duas visões:** alternar entre **por terapeuta** (ocupação/vago) e **por
   paciente** (a semana inteira da criança, cross-terapeuta) — esta é a
   pergunta diária do coordenador e o ponto cego que a v1 tinha.
4. **Alocar:** clicar slot livre → popover com **select de disciplina + select
   de paciente por nome** → confirma → cria `agendamento_recorrente`
   (`vigenciaInicio` = semana corrente). Também permite criar **sessão avulsa**
   (tipo avaliação/devolutiva/reunião) sem regra.
5. **Repetir por N semanas:** materializa as ocorrências das regras ativas
   (pulando bloqueios). Indefinido = horizonte rolling + "estender".
6. **Gerir sessão:** marcar `realizada` / `falta_paciente` / `falta_terapeuta`
   (+ `justificada`) / `cancelada`; registrar **quem atendeu** (substituto);
   **repor** (cria sessão nova com `repostaDe` apontando a original).
7. **Perfil paciente** (nova seção/aba "Horas"): tabela por disciplina —
   alvo vs agendado vs realizado — + alerta "abaixo do prescrito há ≥ 2 semanas".
8. **Perfil terapeuta** (nova rota `/equipe/[id]`): capacidade vs alocado vs
   vago + lista de pacientes fixos.

## 7. Faseamento de execução (detalhado no plano)

> Rótulos internos (Etapa A–F). **Não** confundir com a "Fase 5" do roadmap,
> que já é *Relatórios de Convênio* (Issue #8). Ver §11 para posicionamento no
> roadmap.

- **Etapa A — Fundação de dados:** migrations das tabelas/colunas novas +
  extensão `btree_gist` + constraints (UNIQUE, EXCLUDE, FKs compostas) +
  políticas RLS + alvo-por-disciplina no cadastro de paciente. Testes RLS +
  integridade.
- **Etapa B — Disponibilidade:** `janela_trabalho` + `bloqueio` (UI de config) +
  perfil de terapeuta base (`/equipe/[id]`).
- **Etapa C — Calendário + alocação:** grade semanal (duas visões) +
  select-first + criação de regra e de sessão avulsa + detecção de conflito
  (EXCLUDE).
- **Etapa D — Recorrência:** materialização IANA + "esta e futuras" + estender +
  idempotência.
- **Etapa E — Ciclo de vida da sessão:** estados + substituto (`atendidoPorId`)
  + reposição (`repostaDe`) + modalidade.
- **Etapa F — Métricas:** cálculos por disciplina nos dois perfis + alerta de
  defasagem.

## 8. Testes

- **Lógica pura (unit):** cálculo de horas (agendado/realizado/vago por
  disciplina), detecção de conflito, resolução de "esta e futuras",
  materialização (datas geradas dado regra + bloqueios + timezone).
- **Integração (com Postgres):** RLS das tabelas novas, EXCLUDE gist barrando
  overbook concorrente, UNIQUE barrando materialização duplicada, IDOR via FK
  composta.
- **a11y:** axe nas telas novas (calendário, config de janela, perfis),
  padrão das fases anteriores.
- **DST:** teste dedicado materializando através de uma virada de horário de
  verão para garantir que o slot não desloca.

## 10. Riscos residuais

- **Migração de `session.estado`:** o enum atual é **recriado** (não `ADD
  VALUE`, para remover valores legados deterministicamente numa transação),
  com mapeamento `agendada`→`agendada`, `presente`→`realizada`,
  `falta`→`falta_paciente`. Detalhado na Etapa A.
- **Custo do EXCLUDE gist:** exige extensão `btree_gist` no Postgres de
  produção — confirmar disponibilidade (VPS/Easypanel se o pivô de infra
  ocorrer; ver `docs/arquitetura/plano-bootstrap-e-stack-vps.md`).
- **Grupo/co-terapia (D11):** dívida aceita; quando entrar, exige junções
  `session_participante` / `session_terapeuta` e recálculo das métricas.

## 11. Posicionamento no roadmap (a confirmar com o Rômulo)

Agenda 2.0 **não é** a Fase 5 (Relatórios de Convênio, Issue #8). É uma fase
nova. Observação de sequência: os relatórios de convênio dependem de horas
prescritas vs. realizadas por disciplina — que **só existem depois** desta
agenda. Logo, Agenda 2.0 é candidata a **pré-requisito da Fase 5**. Proposta
pendente de confirmação; o número/ordem oficial fica a critério do Rômulo.
