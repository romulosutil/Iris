# Agenda 2.0 — Etapa A (Fundação de Dados) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Estabelecer a fundação de dados disciplina-aware da Agenda 2.0 — extensão `btree_gist`, colunas novas em `clinic`, quatro tabelas novas (`patient_alvo_disciplina`, `janela_trabalho`, `bloqueio`, `agendamento_recorrente`), enriquecimento de `session` (estados, duração, disciplina, reposição, substituto, modalidade, tipo) com constraints de integridade (UNIQUE de materialização + EXCLUDE anti-overbook), políticas RLS multi-tenant e captura do alvo-por-disciplina no cadastro de paciente.

**Architecture:** Todas as tabelas novas carregam `clinicId` e política RLS `WITH CHECK` no padrão das fases 1–4 (GUCs `app.clinic_id/user_id/user_role` lidos via `current_setting()`; helpers SECURITY DEFINER `app_patient_in_clinic`/`app_user_in_clinic`/`app_is_on_team`). Referências a paciente usam **FK composta `(id, clinicId)`** (anti-IDOR em nível de banco); referências a terapeuta (`app_user`, global, sem `clinic_id`) reusam o guard existente `app_user_in_clinic()` no `WITH CHECK`. Mudanças estruturais expressáveis em Drizzle vão por `pnpm db:generate` (mantêm o snapshot em sincronia); extensão, recriação de enum com migração de dados e constraints `EXCLUDE gist` (não expressáveis em Drizzle) são SQL à mão registrado no `_journal.json` sem snapshot — exatamente como os `*_rls.sql` já existentes (0019 etc. não têm snapshot).

**Tech Stack:** Next.js 16, Drizzle ORM, Postgres (RLS multi-tenant), Vitest, pnpm

## Global Constraints
- **RLS obrigatória em toda tabela nova:** `ENABLE` + `FORCE ROW LEVEL SECURITY`, policies `WITH CHECK` no INSERT/UPDATE (nunca só `USING`), escopadas por `clinic_id = current_setting('app.clinic_id')::uuid`.
- **Anti-IDOR por FK composta `(id, clinicId)`** para paciente; para terapeuta, guard `app_user_in_clinic()` no `WITH CHECK` (padrão de `session_insert`).
- **LGPD:** dado de agenda de um paciente só existe após consent (o gate já vive em `criarPacienteEConsent`; a extensão do cadastro grava o alvo na MESMA transação do paciente+consent).
- **Migrations:** estruturais expressáveis via `pnpm db:generate` (schema.ts → snapshot); não-expressáveis (extensão, enum-recreate, EXCLUDE, RLS) à mão, com entrada manual em `db/migrations/meta/_journal.json` (**sem** arquivo de snapshot — convenção confirmada: 0001/0002/0004/0006/0007/0012/0014/0016/0017/0019 não têm snapshot). Aplicar com `pnpm db:migrate`.
- **Convenção de migração à mão:** cada statement separado por `--> statement-breakpoint`; header comentado explicando o porquê (padrão dos `*_rls.sql`).
- **Migrations rodam como dono** (`MIGRATION_DATABASE_URL`); runtime usa `app_role`. `GRANT ... ON ALL TABLES` da 0001 é point-in-time e **não** cobre tabela nova → `GRANT` explícito em cada RLS nova.
- **Testes de integração:** arquivo `db/tests/*.int.test.ts`, `describe.skipIf(!hasDb)`, harness com `owner = postgres(MIGRATION_DATABASE_URL)` + `withTenant(ctx, tx => …)`. Rodar com `pnpm test:rls`.
- **Commits pt-BR Conventional Commits** (`feat(agenda)`, `test(agenda)`, …), um commit atômico por passo verde.
- **Numeração indicativa:** os números `0021+` abaixo assumem que a última migration é `0020` (idx 20 no journal). `pnpm db:generate` numera a partir do maior idx do journal +1; toda migration à mão precisa estar registrada no journal **antes** do próximo `db:generate`, senão a numeração colide.

### Decisões tomadas por falta de info na spec (revisar com o Rômulo)
1. **FK composta de terapeuta é impossível como escrita na spec** (§3.3/§3.5 dizem `(terapeutaId, clinicId) → app_user`): `app_user` é a tabela global do Better-Auth e **não tem `clinic_id`**. Adotado o padrão já vigente no repo (`session_insert`): anti-IDOR de terapeuta via `app_user_in_clinic(terapeuta_id)` no `WITH CHECK`. Só o paciente ganha FK composta real (`patient` tem `clinic_id`).
2. **Mapa de migração de `session.estado`**: `presente → realizada`, `falta → falta_paciente` (spec §10 deixou em aberto). `presente` era check-in feito ⇒ tratado como atendido; `falta` histórico assumido como falta do paciente. Recreate do type (não `ADD VALUE`) para remover os valores legados deterministicamente numa transação.
3. **Técnica enum**: rodar `db:generate` (para atualizar o snapshot) e **sobrescrever** o corpo do `.sql` gerado pelo recreate com mapeamento — porque o cast naïve do drizzle-kit falharia nas linhas legadas.
4. **`duracaoMin` = `NOT NULL DEFAULT 60`** (spec não fixa default): exigido porque o range do EXCLUDE não aceita bound nulo; linhas legadas recebem 60; app sobrescreve com o default por disciplina.
5. **Escopo de escrita das tabelas de configuração** (`janela_trabalho`, `bloqueio`, `agendamento_recorrente`): apenas `coordenador` (a jornada é "coordenador configura"). `patient_alvo_disciplina`: `coordenador` + `admin_recepcao` (é parte do cadastro administrativo). 7. **`bloqueio.patient_id`** nullable com FK composta MATCH SIMPLE (só checada quando não-nulo) — permite bloqueio de clínica/terapeuta sem paciente.
